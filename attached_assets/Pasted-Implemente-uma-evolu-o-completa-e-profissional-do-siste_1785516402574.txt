Antes de modificar qualquer arquivo, examine a arquitetura atual do projeto, especialmente:

- a página `/admin/characters`;
- o carregamento atual de personagens no Phaser;
- o sistema existente de Sprite Origin;
- o sistema existente de Collision Body;
- o sistema de movimentação click-to-move;
- o painel `/admin`;
- a opção global `Debug Visuals`;

- qualquer configuração antiga relacionada ao personagem `test-character-01`.

Não reescreva sistemas que já funcionam sem necessidade. Integre esta funcionalidade à arquitetura existente.

OBJETIVO PRINCIPAL

Transformar `/admin/characters` em um editor completo de configuração de personagens, permitindo:

1. descobrir automaticamente os personagens existentes nos assets;
2. descobrir automaticamente seus movimentos;
3. dividir spritesheets em direções e frames;
4. configurar Sprite Origin;
5. configurar Collision Body;
6. ativar opcionalmente Hitboxes e Hurtboxes por personagem;
7. configurar Hitboxes e Hurtboxes manualmente, frame a frame;
8. salvar todas as configurações;
9. carregar essas configurações automaticamente no jogo;
10. visualizar todas as marcações quando `Debug Visuals` estiver ativo;
11. alternar temporariamente o personagem jogável para testes.

1. NOVA ESTRUTURA DE ARQUIVOS
==================================================

A pasta-base dos personagens é:

`public/assets/characters`

IGNORE COMPLETAMENTE, por enquanto, esta pasta:

`public/assets/characters/action`

Ela não deve:

- aparecer na página de personagens;
- ser escaneada;
- ser validada;
- gerar warnings;
- ser usada pelo carregador do jogo;
- ser incluída no manifest;
- ser considerada um personagem ou movimento.

Dentro de `public/assets/characters`, cada personagem será uma pasta.

Exemplos:

`character 01 - 4-directions`
`character 02 - 8-directions`
`character 03 - 4-directions`

O parser deve aceitar diferenças de maiúsculas, minúsculas e espaços, como:

`Character01 - 4-Directions`
`character 01-4-directions`
`CHARACTER 01 - 4 DIRECTIONS`

Use uma expressão equivalente a:

`^character\s*0*(\d+)\s*-\s*(4|8)\s*[- ]\s*directions$`

A implementação pode ajustar a regex, mas deve interpretar corretamente:

- o ID numérico do personagem;
- a quantidade de direções, que só pode ser 4 ou 8.

O ID canônico deve ser normalizado como:

`character01`
`character02`
`character03`

O nome visual pode ser:

`Character 01`
`Character 02`
`Character 03`

A quantidade de direções deve ser armazenada separadamente:

`4`
ou
`8`

==================================================
5. DIVISÃO INTELIGENTE DAS SPRITESHEETS
==================================================

O número de linhas da spritesheet é definido pela quantidade de direções do personagem.

Para personagens de 4 direções:

- linha 0: down;
- linha 1: left;
- linha 2: right;
- linha 3: up.

Essa ordem é obrigatória.

Para personagens de 8 direções, usar esta ordem:

- linha 0: down;
- linha 1: down-right;
- linha 2: right;
- linha 3: up-right;
- linha 4: up;
- linha 5: up-left;
- linha 6: left;
- linha 7: down-left.

A detecção automática deve seguir esta lógica:

1. `rowCount = character.directions`;
2. `frameHeight = imageHeight / rowCount`;
3. como regra principal, os frames são quadrados;
4. `frameWidth = frameHeight`;
5. `columnCount = imageWidth / frameWidth`.

Exemplo:

Imagem com:

- largura: 512;
- altura: 512;
- oito direções.

Resultado:

- oito linhas;
- altura de frame: 64;
- largura de frame: 64;
- oito frames por linha.

Validar que:

- `imageHeight / rowCount` seja inteiro;
- `imageWidth / frameWidth` seja inteiro.

Caso a detecção não resulte em valores inteiros, não cortar incorretamente.

Mostrar um aviso e permitir configurar manualmente:

- frame width;
- frame height;
- quantidade de colunas.

Salvar o override no config daquele asset.

Sempre usar nearest-neighbor para ampliar previews de pixel art.

Nunca suavizar os sprites.

8. COLLISION BODY
==================================================

Preserve o Collision Body circular atual.

O Collision Body representa apenas a colisão física do personagem com:

- paredes;
- objetos;
- construções;
- outros obstáculos sólidos;
- navegação e bloqueio no mapa.

Collision Body NÃO é Hurtbox.

Collision Body NÃO é Hitbox.

O Collision Body deve continuar sendo um círculo configurável por:

- offset X em pixels relativo ao Origin;
- offset Y em pixels relativo ao Origin;
- radius em pixels.

Estrutura:

{
  "shape": "circle",
  "offsetX": -0.5,
  "offsetY": 14.8,
  "radius": 10
}

Continuar permitindo:

- arrastar o círculo vermelho;
- alterar o radius;
- editar valores numericamente;
- visualizar a linha verde dos pés/contato com o chão.

A linha dos pés pode continuar sendo derivada da parte inferior do Collision Body, preservando o comportamento atual.

Não substituir a lógica de destino do Sprite Origin pela posição do círculo.

O Origin continua definindo onde o jogador para.

O Collision Body continua definindo onde ele colide.

21. MOVIMENTAÇÃO DE PERSONAGENS COM 4 DIREÇÕES
==================================================

Implementar o personagem de quatro direções como jogável no mapa.

A ordem obrigatória das linhas é:

- row 0: down;
- row 1: left;
- row 2: right;
- row 3: up.

A direção visual deve ser escolhida pelo vetor de movimento.

Usar:

- se `abs(deltaX) > abs(deltaY)`, escolher left ou right;
- caso contrário, escolher up ou down.

Exemplo:

if Math.abs(dx) > Math.abs(dy):
  direction = dx < 0 ? "left" : "right"
else:
  direction = dy < 0 ? "up" : "down"

O personagem pode continuar se movendo diagonalmente no mundo, caso esse seja o comportamento atual do jogo, mas a animação visual deve usar uma das quatro direções cardinais.

Preservar:

- click-to-move;
- pathfinding;
- velocidade;
- interpolação;
- sincronização multiplayer;
- parada no ponto definido pelo Sprite Origin.

Ao parar:

- tocar `idle` da última direção;
- caso não exista idle, congelar um frame apropriado de walk.
