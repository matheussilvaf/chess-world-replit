==================================================
1. CONTEXTO E MUDANÇA DE ARQUITETURA
==================================================

Anteriormente, `/admin/characters` configurava personagens fixos descobertos dentro de:

`public/assets/characters`

Esse modelo deixa de ser a arquitetura principal.

Os jogadores passarão a criar personagens visuais dinamicamente por meio do Character Generator. Cada jogador poderá ter sua própria spritesheet PNG montada e salva no servidor.

Esses PNGs personalizados não devem possuir configurações individuais de colisão.

A nova arquitetura deve separar:

1. APARÊNCIA:
   - PNG composto e personalizado de cada jogador;
   - cabelo;
   - cabeça;
   - top;
   - bottom;
   - chapéu;
   - arma;
   - tom de pele;
   - demais camadas.

2. RIG:
   - Sprite Origin;
   - Collision Body;
   - Hurtboxes;
   - Hitboxes;
   - mapeamento de animações;
   - mapeamento de direções e frames.

Todo personagem gerado pelo Character Generator deve possuir um `rigId`.

Exemplo:

{
  "characterId": "player-character-483",
  "rigId": "time-elements-humanoid-v1",
  "spriteUrl": "/api/characters/player-character-483/sprite",
  "appearanceVersion": 4
}

Todos os personagens que utilizarem:

`time-elements-humanoid-v1`

devem herdar exatamente as mesmas configurações físicas e de combate, independentemente da aparência visual.

11. SPRITE ORIGIN
==================================================

Preserve o editor atual de Sprite Origin.

O Origin é uma propriedade global do rig.

Ele não pertence à aparência do jogador.

Ele não deve ser duplicado em cada animação ou frame.

Estrutura:

{
  "x": 0.5,
  "y": 0.5
}

Manter:

- crosshair ciano;
- arrastar;
- campos X e Y;
- botão Centralizar;
- valores normalizados entre 0 e 1;
- snap configurável;
- preview em tempo real.

No jogo, o Origin deve continuar sendo o ponto usado para posicionar o personagem no mundo e para o destino do click-to-move.

Não usar o centro geométrico do PNG quando o Origin configurado for diferente.

==================================================
12. COLLISION BODY
==================================================

Preserve o editor circular atual de Collision Body.

O Collision Body é global do rig.

Ele representa colisão com:

- mapa;
- paredes;
- objetos;
- construções;
- obstáculos sólidos.

Ele não representa dano.

Estrutura:

- campos numéricos;
- linha verde de contato com os pés.

O Collision Body deve ser relativo ao Sprite Origin.

Não confundir Collision Body com Hurtbox.

==================================================
13. HURTBOXES
==================================================

Hurtbox representa a área que pode receber dano.

As Hurtboxes pertencem ao rig e devem ser configuráveis por:

- animação;
- direção;
- frame.

Permitir uma ou várias Hurtboxes retangulares por frame.

Por padrão:

- Hurtbox desabilitada;
- lista vazia.

Estrutura:

{
  "enabled": true,
  "rectangles": [
    {
      "id": "hurtbox-1",
      "x": -12,
      "y": -32,
      "width": 24,
      "height": 36
    }
  ]
}

As coordenadas são relativas ao Sprite Origin.

Usar pixels originais do frame 96×96.

Não salvar coordenadas ampliadas do Canvas.

Cor visual:

- verde ou verde-limão.

Permitir:

- criar;
- selecionar;
- arrastar;
- redimensionar;
- duplicar;
- excluir;
- editar X/Y/Width/Height;
- múltiplas caixas;
- copiar de outro frame.

==================================================
14. HITBOXES
==================================================

Hitbox representa a área que causa dano.

As Hitboxes devem ser configuráveis por:

- animação;
- direção;
- frame.

Por padrão:

- Hitbox desabilitada;
- lista vazia.

Estrutura:

{
  "enabled": true,
  "rectangles": [
    {
      "id": "hitbox-1",
      "x": -30,
      "y": 2,
      "width": 60,
      "height": 24
    }
  ]
}

Cor visual:

- magenta, roxo forte ou laranja.

Não utilizar a mesma cor do Collision Body.

Permitir:

- criar;
- selecionar;
- arrastar;
- redimensionar;
- duplicar;
- excluir;
- múltiplas caixas;
- edição numérica;
- copiar entre frames.

A Hitbox nunca deve ser criada automaticamente com base nos pixels da arma.

Ela deve existir somente nos frames configurados manualmente.

==================================================
15. METADADOS DE DANO DA ANIMAÇÃO
==================================================

Preserve e adapte os controles atualmente existentes:

- `Dano ativo neste movimento`;
- `Dano por acerto`;
- `Ativas no jogo`.

Esses dados devem pertencer à configuração da animação dentro do rig.

Exemplo:

{
  "combat": {
    "enabled": true,
    "damagePerHit": 10,
    "singleHitPerTarget": true
  }
}

Regras:

- sem Hitbox ativa em nenhum frame, a animação não causa dano;
- `combat.enabled = false` impede o dano, mesmo que existam caixas para debug;
- cada ataque deve atingir o mesmo alvo apenas uma vez por execução, salvo configuração futura explícita;
- o cliente não decide o dano;
- o servidor Colyseus deve ser a autoridade.

24. COLYSEUS E AUTORIDADE DO SERVIDOR
==================================================

O Phaser pode mostrar as caixas e prever visualmente o ataque.

O Colyseus deve decidir o dano.

Ao atacar, o cliente envia apenas uma intenção:

{
  "type": "attack",
  "animation": "attack-full",
  "direction": "south"
}

O servidor obtém:

- jogador;
- rigId;
- configuração do rig;
- animação;
- direção;
- frame autoritativo;
- Hitboxes do frame;
- Hurtboxes dos possíveis alvos.

O servidor converte as caixas locais para coordenadas do mundo e testa interseções.

Não confiar em:

- dano enviado pelo cliente;
- targetId declarado como acertado;
- Hitboxes enviadas pelo cliente;
- posição de caixa enviada pelo cliente.

Criar geometria compartilhada sem dependência de Phaser no servidor.

==================================================
